# ROUND 점검

검토 종류는 `$ARGUMENTS`나 요청 문장으로 정한다. 검토만 요청받으면 결과를 보고하고, 반영까지 요청받았으면 항목별로 수정·검증·기록한다.

## 공통 기준

- 시작할 때 `git rev-parse --short HEAD`를 검토 기준으로 기록한다.
- 아래 기존 기록의 제목부터 확인해 이미 반영했거나 유지하기로 한 항목을 다시 제안하지 않는다. 같은 파일을 다시 볼 때는 새 요구사항·실제 오류·계약이나 의존성 변경 같은 근거가 있어야 한다.
- 방 생성·스터디 관리는 BATON, 입장 준비·통화는 ROUND 담당이다. BATON 영역 제안은 ROUND에 구현하지 않고 보고만 한다.
- 추가 요금이 생기는 외부 서비스는 제안하지 않는다(`docs/external-api-review.md`의 기존 결정).
- 코드 위치와 재현 조건이 있는 문제만 항목으로 만든다. 확인한 사실과 추정을 구분한다.
- 반영할 때는 동작에 따라 `round-webrtc-flows`·`round-spring-signaling`, 브라우저 확인은 `round-e2e`, 마무리는 `round-finish` 스킬을 사용한다.

## 기능

- 기존 기록: `docs/feature-review.md` (`grep -n '^## '`)
- 입장 준비 → 통화 → 채팅 → 재연결 → 퇴장 흐름에서 진행 중 상태 유실, 창 재열기·취소·중복 요청, 실패 후 복구, 모바일·키보드 사용을 확인한다.
- 기록은 파일 맨 위에 추가한다.

  ```markdown
  ## <제목>: YYYY-MM-DD

  검토 기준은 `<sha>`이다. <문제와 영향 1~2문장>

  - <바뀐 동작>
  - <유지할 동작·제한>
  ```

## 문구

- 기존 기록: `docs/copy-review.md`. "적용 시 유지할 의미" 절은 항상 지킨다.
- 대상은 `apps/web/src`의 화면·오류 안내·접근성 문구(`aria-label` 등)와 주요 문서다.
- 사용자가 누를 버튼과 확인할 상태를 구체적으로 적고, 의미 없는 수식어와 내부 구현 설명을 줄인다. 기술 문서의 정확한 용어(WebRTC·TURN·JWT·SDP·ICE 등)는 유지한다.
- 바꾼 문구는 `rg -n '<기존 문구>' apps/web e2e`로 테스트·e2e 선택자까지 함께 고친다.
- 기록은 `## YYYY-MM-DD <제목>` 절에 `번호 | 위치 | 검토 당시 문구 | 반영 문구 | 이유` 표로 남긴다.
- 검증은 바뀐 테스트 파일의 `npm run check:web -- <파일>`. e2e 선택자나 배치가 바뀐 경우에만 해당 브라우저 검사를 실행한다.

## 코드

- 기존 판단: `docs/java-spring-review.md`의 "유지할 코드", `output/agent-validation.md`의 추가 점검·유지 근거.
- 같은 처리 안의 중복은 실패 시점과 동작이 같을 때만 제거한다. 브라우저와 서버의 입력 검증, 인증, 서로 다른 자원 제한, 비동기 응답 무시, 브라우저별 지원 확인은 유지한다.
- 줄 수를 줄이려고 보조 함수를 추가하거나 새 의존성·공개 인터페이스를 늘리지 않는다.
- 제거할 실익이 분명한 항목이 없으면 코드를 바꾸지 않고, 확인 범위와 유지 근거를 보고·기록한다.

## 디자인

- 기존 기록: `docs/design-review.md`. 전면 개편보다 부분 보완을 우선하고 변경은 `apps/web/src/styles.css`에 한정한다. 외부 글꼴·이미지·새 의존성은 추가하지 않는다.
- Chromium·WebKit에서 1280px·390px·320px 폭, 2명·6명 배치, 채팅·장치 설정, 키보드 초점을 확인한다. 주요 버튼 글자 대비는 4.5:1 이상을 유지한다.
