서버와 모바일 실장치에서의 운영 검증은 파일럿 범위로 남긴다.

ROUND의 사용자 진입은 BATON의 스터디 화면과 공유받은 방 링크로 통일하는 방향을 권장한다.
별도 ROUND 메인에서 방을 찾거나 만드는 절차보다, 특정 방의 입장 준비와 통화에 집중한다.
검토 후 화면 흐름을 변경했으며 기존 인증 계약은 유지했다.

검토 당시 [App](../apps/web/src/App.tsx)은 BATON 모드의 방 없는 경로에 BATON 복귀 안내를
표시한다. 그러나 유효한 방에서 권한 확인을 통과한 뒤에도
[LandingScreen](../apps/web/src/components/LandingScreen.tsx)의 소개 문구·기능 미리보기·
이름 입력을 거쳐 다시 장치 준비 화면으로 이동한다. 이 화면의 `다른 방 만들기`도 실제
BATON 모드에서는 BATON 홈으로 돌아가는 동작이라 문구와 목적지가 맞지 않는다.

권장 진입 흐름은 다음과 같다.

- BATON 스터디의 통화 참여 → 해당 방의 권한 확인 → 입장 준비 → 통화
- 공유받은 방 링크 → 필요한 경우 BATON 로그인과 해당 방 복귀 → 권한 확인 → 입장 준비 → 통화
- 통화 종료 → BATON 복귀. 스터디 상세로 돌아가려면 BATON이 제공하는 복귀 경로 계약을 먼저 확인한다.

입장 준비에는 이름 확인, 카메라·마이크 설정과 입장 버튼을 모은다. BATON 계정 이름을
자동으로 채우려면 서버가 제공하는 이름 계약이 필요하다. 현재의 임시 표시 이름을 계정
이름으로 간주하지 않는다. 이름을 받기 위해 소개 화면을 별도로 거칠 필요는 없다.
방 생성과 스터디 관리는 BATON에서 담당하고, 기존 독립 실행 화면은 개발·검증 용도로
남길 수 있다. 실제 운영에서 노출할 진입 경로와 구분한다.

공유 링크는 방으로 가는 주소이며 현재의 로그인·멤버십·방 참여 권한 확인을 유지한다.
링크만으로 비회원에게 참여를 허용하는 정책은 별도 결정 사항이다. 링크를 열었다는 이유로
카메라·마이크를 자동으로 켜지 않고 입장 준비에서 사용자의 장치 확인 동작을 유지한다.

구현 시에는 BATON 진입과 공유 링크가 같은 준비 화면으로 합쳐지는지, 로그인 후 같은 방으로
돌아오는지, 권한 거절·종료된 방 안내와 퇴장 후 복귀가 맞는지 확인한다.

해제되지 않고, 승인 시 기존 세션 정리가 한 번만 실행되는지 확인한다.

내용에 따라 최대 4~5줄까지 입력창 높이를 늘리고, 남은 입력량과 줄바꿈 방법을 안내한다.

조합 처리를 유지하며, 글자 수 표시는 현재 길이 검사와 같은 계산 기준을 사용한다.

최소 검증은 여러 줄 입력·전송 후 높이 복원, 한도 근처의 입력·붙여넣기, 한글 조합,
320px 화면에서 입력창과 보내기 버튼의 배치다.

## 1. 실패한 참가자만 다시 연결

**현재 동작:** [RoomView](../apps/web/src/components/RoomView.tsx)의
`peerRecoveryMessage` 안내는 `방 다시 입장`을 제공한다.
[App](../apps/web/src/App.tsx)의 `retryCurrentRoom`은 활성 방을 해제하고 입장 전 화면으로
돌아간다. [ActiveRoom](../apps/web/src/components/ActiveRoom.tsx)이 정리되면서 기존
`RoomSession`을 종료하므로 정상 상대와의 연결도 닫히고, 새 세션에는 이전 채팅 기록이 없다.
시그널링의 자동 재연결이 기존 로컬 미디어와 채팅 기록을 유지하는 동작과는 구분해야 한다.

**개선안:** 실패한 참가자의 타일에 `이 참가자 다시 연결`을 제공한다. 정상 상대와의
통화, 로컬 장치, 음소거 상태, 기존 채팅 기록을 유지하고 해당 연결만 다시 협상한다.
전체 방 연결이 끝난 경우에는 현재 재입장 흐름을 유지한다.

**구현 시 확인할 점:**

- [RoomSession](../packages/rtc-core/src/room-session.ts)의 `#failPeer`와
  `#failPeerConnectionTimeout`은 실패한 피어를 정리하고 `#exhaustedPeerIds`에 기록한다.
  그 피어의 후속 offer·answer·ICE도 무시하므로, 버튼에서 기존 ICE 재시작 함수만 호출하면
  양쪽이 모두 재시도를 소진한 경우를 복구할 수 없다.
- 사용자 재시도에 대한 양쪽 상태 초기화와 새 협상 ID 처리 규칙이 필요하다. 이전 실패
  협상의 늦은 메시지를 받아들이지 않으면서 새 복구 요청을 구분해야 한다.
- 시그널링 메시지를 추가한다면 같은 방의 현재 참가자만 대상으로 허용하고 TypeScript와
  Java 계약을 함께 변경한다. 반복 클릭은 진행 중인 복구 한 번으로 합친다.

**최소 검증:** 3명 중 한 상대만 양쪽에서 실패한 상황을 만들고 한쪽의 사용자 재시도로
복구되는지 확인한다. 정상 연결과 채팅 기록이 유지되고, 대상 퇴장이나 방 나가기 후에는
복구 작업이 남지 않아야 한다.

WebRTC의 `restartIce()`도 다음 offer와 시그널링 교환이 필요하다. 따라서 ROUND의
협상·재시도 상태와 함께 연결해야 한다.
[MDN의 ICE 재시작 설명](https://developer.mozilla.org/en-US/docs/Web/API/RTCPeerConnection/restartIce)

## 2. 채팅 수신 미확인 대상 표시와 선택 재전송

**현재 동작:** [RoomChatPanel](../apps/web/src/components/RoomChatPanel.tsx)은
`일부 참가자 수신 확인 실패`나 `수신 확인 실패`를 표시한다. 메시지 복사는 가능하지만
수신자별 결과나 재전송 버튼은 없다.
[RoomChatLedger](../packages/rtc-core/src/room-chat.ts)는 대기 중에 수신자별 상태를
관리하지만 최종 상태가 정해지면 해당 맵을 삭제한다. 화면용 `ChatMessage`에도 합산 결과만
있다. 따라서 화면에 버튼만 추가해서 처리할 수 있는 작업은 아니다.

**개선안:** 메시지별로 `3명 중 2명 수신 확인`과 수신 미확인 대상 목록을 표시하고,
현재 같은 피어로 남아 있는 대상에게만 사용자가 재전송할 수 있게 한다.

**구현 시 확인할 점:**

- 수신 확인 실패는 메시지가 도착하지 않았다는 확정 결과가 아니다. 메시지는 도착하고 ACK만
  유실될 수 있으므로 사용자 문구도 `수신 미확인`으로 유지한다.
- 이미 ACK한 대상은 제외한다. 같은 메시지 ID로 재시도하려면 수신 측 중복 제거 기록의
  보관 범위와 재시도 가능 시간을 함께 정해야 한다. 무제한 재전송은 제공하지 않는다.
- 최종 수신자 상태도 현재 채팅 보관 한도 안에서만 유지한다. 늦게 입장한 사람에게 이전
  메시지를 보내거나, 재입장한 사람을 표시 이름만으로 이전 수신자와 연결하지 않는다.
- 사람의 읽음 여부는 알 수 없으므로 수신 확인을 `읽음`으로 표시하지 않는다.

**최소 검증:** 정상 ACK 대상과 미확인 대상이 섞인 상태, ACK만 유실된 상태, 대상 퇴장,
재전송 가능 시간 만료를 확인한다. 이미 수신한 메시지가 중복 표시되지 않아야 한다.

## 3. 참가자별 통화 품질 안내

**현재 동작:** [연결 진단](../apps/web/src/components/ConnectionDiagnosticsPanel.tsx)은
사용자가 열거나 새로고침할 때 수신 손실·지연·지연 변동을 측정한다. 참가자 타일은 주로
연결 상태를 표시하므로 연결이 유지된 상태의 끊김은 진단을 직접 열어야 살펴볼 수 있다.
[카메라 송신 설정](../apps/web/src/components/MediaDeviceDialog.tsx)에는 이미 수동
데이터 절약 모드가 있다.

**개선안:** 사용자가 켤 수 있는 통화 품질 표시를 제공한다. 연속된 측정에서 문제가
관측된 참가자에게만 `이 참가자의 수신이 불안정합니다`를 표시하고 진단으로 연결한다.
초기 범위는 안내까지로 제한하고 자동 화질 변경은 측정 결과를 확보한 뒤 검토한다.

**구현 시 확인할 점:**

- 현재 수신 통계를 근거로 내 카메라 송신 품질을 낮추면 상대 영상의 수신 문제가 해결된다고
  안내해서는 안 된다. 송신과 수신, 음성과 영상을 구분해야 한다.
- 지원되는 경우 디코딩 프레임·영상 멈춤 통계를 보조 지표로 사용할 수 있다. 다만 정적인
  공유 화면과 영상이 꺼진 상태를 장애로 오인하지 않아야 한다.
  [MDN의 수신 RTP 통계](https://developer.mozilla.org/en-US/docs/Web/API/RTCInboundRtpStreamStats)
- 기존 진단의 주소·방 코드·이름 제외 정책을 유지한다. 참가자와의 대응은 현재 화면에서만
  사용하고 복사하는 진단 결과에는 포함하지 않는다.
- 주기적 측정을 도입할 때에는 기존의 요청 시 측정 정책 변경을 문서화하고, 중복 측정과
  숨겨진 탭의 불필요한 작업을 막는다. 미지원 통계는 정상값 대신 측정 불가로 처리한다.

**최소 검증:** 잠깐의 손실에는 알림이 깜박이지 않고, 지속 문제와 복구가 화면에 반영되는지
확인한다. 카메라 끄기와 통계 미지원 상태에서도 잘못된 경고가 나오지 않아야 한다.

## 4. 문서·코드용 화면 공유 품질 선택

**현재 동작:** [ScreenShareLifecycle](../packages/rtc-core/src/screen-share-lifecycle.ts)의
캡처 설정은 최대 1280×720, 15fps이며 `contentHint = 'detail'`을 적용한다. 원격 화면의
크게 보기와 전체 화면은 이미 제공한다. 화면 공유는 카메라용 데이터 절약 제한에서 제외된다.

**개선안:** 현재 설정을 기본으로 유지하고, 문서나 코드를 공유할 때 선택할 수 있는 선명도
모드를 검토한다. 예를 들어 1080p 캡처와 낮은 프레임 수의 조합을 시험하고, 실제 글자
가독성과 통화 품질을 비교한 뒤 기본값을 결정한다. 720p 때문에 실제로 읽기 어렵다는
사용자 제보나 실장치 재현은 이번 검토에서 확보하지 않았다.

`contentHint`의 `text`는 글자처럼 경계가 뚜렷한 화면을 위한 힌트다. 기존 `detail`과
비교할 수 있지만 특정 선명도를 보장하는 설정은 아니다.
[MDN의 콘텐츠 힌트 설명](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/contentHint)

**최소 검증:** 실제 코드·문서를 공유해 수신 화면의 가독성을 비교한다. 2명과 6명에서
송신량, CPU 사용량, 음성 끊김을 함께 확인하고, 품질 적용 실패 시 기존 공유를 유지한다.
캡처 해상도를 바꾸면 기존 카메라로 돌아오는 흐름도 확인한다.

## 5. 손들기

**현재 동작:** [DataChannel 계약](../packages/protocol/src/data-channel.ts)은 채팅,
수신 ACK, 미디어 상태를 다룬다. 발언 의사를 나타내는 상태는 없다.

**추가안:** `손들기 / 손 내리기` 버튼과 참가자 배지를 제공한다. 발표자가 말하는 중에도
질문 의사를 전달할 수 있고 별도 저장 서버가 필요하지 않다.

**구현 범위:** 자신의 손들기 상태만 변경하고, 채널이 열릴 때 현재 상태를 보내 늦게
입장한 사람에게도 표시한다. 퇴장하면 상태를 지운다. 최초 버전은 손을 든 사람의 표시까지만
제공한다. 모든 참가자에게 동일한 발언 순서를 보장하려면 별도 순서 결정 규칙이 필요하다.
현재 파서가 모르는 프레임을 거부하므로 웹 배포 호환성도 함께 정한다.

**최소 검증:** 늦은 입장과 채널 복구 후 상태가 맞는지, 퇴장한 사람의 배지가 남지 않는지
확인한다. 채팅 큐를 막을 정도의 반복 전송은 허용하지 않는다.

## 6. 실제 발언 중 표시

**현재 동작:** [VideoTile](../apps/web/src/components/VideoTile.tsx)의 마이크 표시는
`audioEnabled`에 따른 켜짐 상태다. 실제 음성 입력 여부를 뜻하지 않는다.
[MicrophoneLevel](../apps/web/src/components/MicrophoneLevel.tsx)은 입장 전 화면과
장치 설정에서 내 마이크 입력을 확인하는 용도로만 사용한다.

**추가안:** 실제 음성이 관측되는 참가자 타일에 발언 중 표시를 추가한다. 음성 위주로
스터디할 때 발언자를 쉽게 찾을 수 있다. 자동으로 타일 위치를 바꾸기보다는 테두리와
문구만 표시하는 작은 범위로 시작한다.

**구현 범위:** 원격 수신 음성의 레벨을 브라우저에서 계산한다. 기존 마이크 표시를
참가자마다 그대로 복제하기 전에 수신 통계의 `audioLevel` 지원 여부를 확인한다. 미지원
브라우저에서는 발언 표시를 생략해도 통화는 유지한다. 녹음이나 서버 전송은 필요하지 않다.

**최소 검증:** 음소거, 트랙 교체, 참가자 퇴장 뒤 표시가 남지 않고 짧은 배경 소음에
과도하게 반응하지 않는지 확인한다.

## 7. 공용 집중·휴식 타이머와 현재 주제

**현재 동작:** 방의 프로토콜에는 타이머나 진행 주제가 없다. 방장 기능은 다른 참가자의
미디어 끄기 요청에 한정되어 있다.

**추가안:** 방장이 집중·휴식 타이머를 시작·일시정지·초기화하고 짧은 현재 주제를
설정하면 모든 참가자가 같은 상태를 볼 수 있게 한다. BATON의 예약 일정이나 출석 기록과
구분하여 현재 방에서만 쓰는 진행 정보로 한정한다.

**구현 범위:** 브라우저마다 카운터를 독립적으로 감소시키면 늦은 입장과 백그라운드 복귀
시각이 어긋날 수 있다. 시그널링 서버가 상태와 개정 번호, 남은 시간을 관리하고 입장 시
전달하는 방식이 적합하다. 브라우저는 받은 상대 시간을 기준으로 표시하며 다시 동기화한다.
방장이 여러 명일 때 변경 순서와 방장 퇴장·서버 재시작 시 동작도 정해야 한다.

**최소 검증:** 늦은 입장, 일시정지, 동시 조작, 백그라운드 복귀에서 같은 진행 상태를
표시하는지 확인한다. 일반 참가자가 방장 명령을 보낼 수 없어야 한다.

## 사용 범위가 넓어질 때 검토할 기능

- **입장 잠금·퇴장·재입장 제한:** 멤버 외 사용자에게 방을 공개할 때 우선순위를 높인다.
  BATON은 멤버십, ROUND는 현재 방의 입장 상태를 관리하도록 유지한다. 현재 메시 구조에서
  서버의 시그널링 차단만으로 변조된 클라이언트 사이의 기존 미디어까지 강제 종료한다고
  보장할 수 없다는 경계도 명시해야 한다.
- **탭 소리 공유:** 현재 화면 캡처는 `audio: false`다. 영상 자료를 함께 보는 요구가 실제로
  생기면 별도 선택 기능으로 검토한다. 마이크 음성과의 조합, 중지 시 정리, 지원 브라우저
  확인이 필요하다.
- **녹화·채팅 영구 저장·대규모 통화:** 현재의 휘발성 소규모 방과 운영 범위가 달라진다.
  실제 요구가 확인된 후 보관 정책과 미디어 구조를 별도 설계한다.
