# ROUND 아키텍처

ROUND는 아래 네 구성요소로 나뉘며 BATON과 독립적으로 배포할 수 있습니다.
ROUND 시그널링 서버는 별도로 실행하며, BATON과 인증된 요청으로 연동합니다.

```text
apps/web          React 스터디룸 화면
apps/signaling    Java 21 + Spring Boot WebSocket 시그널링 서버
packages/protocol 버전으로 관리하는 시그널링·DataChannel 메시지 계약
packages/rtc-core 프레임워크에 의존하지 않는 WebRTC 엔진
```

## 연결 구조

각 참가자는 원격 참가자마다 하나의 `RTCPeerConnection`을 엽니다. 오디오, 영상, 채팅
데이터는 브라우저 사이를 직접 이동합니다. 시그널링 서버는 참가자 연결에 필요한
SDP/ICE 메시지를 전달하고 방의 타이머·현재 주제를 임시 관리합니다. 직접 경로를 사용할 수 없으면 Cloudflare TURN이 암호화된
WebRTC 패킷을 중계하며, 그 미디어 내용을 Java 애플리케이션에 노출하지 않습니다.

이 메시(mesh) 구조는 첫 버전을 저렴하게 자체 호스팅할 수 있게 합니다. 참가자가 늘어날수록
업로드 대역폭과 CPU 사용량이 증가하므로 의도적으로 참가자를 6명으로 제한합니다.

## BATON과 공유 링크의 입장 흐름

BATON의 통화 참여와 공유 링크는 같은 `/room/{roomId}`로 연결됩니다. BATON 모드는
로그인·방 참여 권한 확인 후 바로 입장 준비 화면을 표시합니다. 소개·기능 미리보기와
별도 이름 입력 화면은 거치지 않습니다. 공유 링크도 기존 멤버십·방 권한 확인을 유지하며,
로그인이 필요하면 로그인 후 정규 방 주소로 돌아옵니다.

입장 준비에서 통화용 이름과 카메라·마이크를 설정합니다. 이름은 준비 화면 안에서 관리해
수정할 때 미리보기나 장치 컨트롤러를 다시 만들지 않습니다. 입장할 때 공백을 정리한 이름을
방 세션에 전달하고, 빈 이름이면 입력칸으로 안내합니다. 장치 확인은 이름 입력과 독립적으로
직접 실행할 수 있지만, 미디어를 사용하거나 사용하지 않는 입장 모두 이름이 필요합니다.
장치 확인 전에는 카메라·마이크를 요청하지 않습니다.

현재 BATON 계약에는 계정 표시 이름이 없으므로 계정 이름 자동 입력은 하지 않습니다.
BATON 모드의 이름은 페이지 메모리에만 보관하고, 독립 실행에서는 기존 로컬 이름 저장을 유지합니다.
BATON의 준비 화면 취소·통화 종료는 BATON 홈으로 돌아갑니다. 특정 스터디 상세로 복귀하는
주소나 비회원 초대 권한을 임의로 추가하지 않습니다.

통화 화면의 초대 창은 검색 조건과 인증 정보를 제거한 정규 방 주소만 QR 코드·클립보드·
브라우저 공유 메뉴에 전달합니다. 공유 메뉴가 열려 있는 동안 중복 실행을 막고 완료 여부를
표시합니다. 사용자가 공유를 취소한 경우에는 오류로 처리하지 않으며, 실제 실패에는 링크 복사를
안내합니다.

독립 실행의 루트 화면에는 개발·검증을 위한 방 생성·코드 입력을 유지합니다. 독립 실행의
방 링크도 같은 입장 준비 화면을 사용하며, BATON 번들에서는 독립 실행의 루트 화면을
노출하지 않습니다.

## 패키지별 역할과 의존성

- `@round/rtc-core`는 React, 라우터, CSS 프레임워크에 의존하지 않습니다.
- `@round/protocol`은 브라우저에서 주고받는 메시지의 타입과 실행 시 검증을 담당합니다.
- `apps/signaling`은 WebSocket으로 받은 메시지를 프로토콜 v3 규칙으로 검증하고
  `com.personal.round.signaling` 아래의 메모리에 방 상태를 보관합니다.
- `apps/web`은 방 상태를 React에 맞게 변환하고 화면을 표시합니다.
- ROUND는 방 ID의 내부 의미를 해석하지 않습니다. BATON은 피어 엔진을 변경하지 않고 참여권을 발급하기
  전에 해당 방을 승인합니다.

## 참가자별 수동 재연결

자동 재연결에 모두 실패한 참가자의 영상 타일에서 `이 참가자 다시 연결`을 누르면 `peer.reconnect`
요청을 보냅니다. 서버는 같은 방의 현재 참가자인지 확인한 뒤 양쪽에 동일한 `connectionId`와
각자의 offer 시작 여부를 보냅니다. 두 참가자 ID를 비교해 한쪽만 offer를 시작합니다.
브라우저는 해당 연결만 새로 만들고 모든 후속 협상 번호에 `connectionId.` 접두사를 붙여
이전 연결의 늦은 SDP·ICE를 거부합니다. 정상 연결, 로컬 미디어, 손들기와 채팅 기록은 유지합니다.
요청 중 반복 클릭은 합치고 10초 동안 서버 응답이 없으면 다시 시도할 수 있게 합니다.
요청을 보내지 못하면 해당 참가자 타일에서 다시 시도하도록 안내합니다. 다음 요청이 접수되거나
연결 상태가 바뀌면 이전 실패 안내를 해제합니다. 참가자 퇴장·방 종료·시그널링 재연결 시 요청
타이머와 연결 번호를 정리합니다.

## 공용 스터디 진행 상태

`room.study.sync`는 현재 방의 `room.study.state`를 요청합니다. `room.study.update`는
`expectedRevision`과 `start|pause|resume|reset|topic` 명령을 보냅니다. 시작 명령은
`focus|break`와 60~7200초를 받고 주제는 빈 문자열을 포함해 최대 120자입니다.
서버가 인증한 방장만 변경할 수 있으며 일반 참가자에게도 최신 상태 조회를 허용합니다.
모든 변경은 기존 방 잠금 안에서 처리합니다. 개정 번호가 다르면 변경하지 않고
`conflict=true`와 최신 상태를 요청자에게 반환합니다. 성공한 변경은 방 전체에 알립니다.

서버는 단조 증가 시계로 남은 시간을 계산하고 브라우저는 응답을 받은 시점을 기준으로
표시합니다. 조회 응답에는 왕복 시간의 절반을 보정하며, 입장·탭 복귀·네트워크 복귀와
화면이 보이는 동안 15초마다 다시 동기화합니다. 요청 결과를 10초 안에 받지 못하면 최신 상태를
다시 조회합니다. 화면의 시간은 네트워크 지연만큼 오차가 있을 수 있고 서버 상태를 기준으로 맞춥니다.

진행 중이거나 일시정지한 진행 시간이 남아 있을 때 새 타이머 시작·초기화를 누르면 현재
남은 시간과 변경 내용을 확인합니다. 취소와 Esc는 명령을 보내지 않고 기존 타이머를 유지합니다.
첫 시작과 이미 완료된 타이머에는 확인을 요구하지 않습니다. 확인 중에는 시간이 계속 흐르며,
다른 상태 개정·권한 상실·연결 중단이 반영되면 확인을 취소하고 최신 상태를 안내합니다.
승인 시 확인창을 열었던 개정 번호를 RTC 코어에 전달합니다. 코어의 최신 개정과 다르면
전송하지 않으며, 전송 뒤 서버에서 생긴 충돌은 기존 `expectedRevision` 계약으로 거부합니다.

방장이 퇴장해도 타이머는 진행됩니다. 종료 후 다음 집중·휴식으로 자동 전환하지 않습니다.
서버 연결이 활성 상태이고 서버가 알려 준 참가자 중 방장이 없으면 접힌 타이머에도
**방장 없음**을 표시합니다. 펼치면 주제·타이머 변경을 할 수 없다는 안내를 제공합니다.
방장의 미디어 연결 실패를 퇴장으로 취급하지 않으며 다른 참가자에게 방장 권한을 넘기지 않습니다.
마지막 참가자가 퇴장하거나 서버가 재시작되면 주제와 타이머를 삭제합니다. BATON의 같은
참가자 연결 교체에서는 방 상태를 유지합니다. 예약 일정·출석·영구 저장과 연결하지 않습니다.

실행 중인 타이머를 관찰한 브라우저는 0초가 되면 서버에 상태를 조회하고, 서버가 종료를
확인한 뒤 화면 알림과 탭 제목으로 안내합니다. 이미 끝난 타이머에 늦게 입장하면 알리지
않으며, 같은 개정 번호의 시간 보정이나 반복 조회로 종료를 다시 알리지 않습니다.
알림음을 직접 켠 동안만 오디오 자원을 유지하고 기기 기본 스피커로 짧은 소리를 냅니다.
알림음을 끄거나 방을 나가면 자원을 닫습니다. 브라우저가 백그라운드 실행이나 소리를
중단하면 알림이 늦거나 무음일 수 있으며, 탭 복귀 때 시간을 다시 확인합니다.

## 입장 전 버전 확인과 새 배포 안내

웹 빌드마다 식별자를 만들고 번들과 `release.json`에 같은 값을 넣습니다. 동일한 빌드의
전체 산출물을 함께 배포해야 합니다. 경로는 독립 실행 `/release.json`, BATON
`/round-ui/release.json`이며 조회는 `no-store`로 처리합니다. 화면이 보이는 동안 60초마다,
탭·네트워크 복귀와 입장 버튼을 누를 때 최신 식별자를 확인합니다. 새 빌드이거나 조회에
실패하면 입장을 멈추고 새로고침·재시도를 안내합니다. BATON 입장 준비에서는 입장 버튼을
누를 때 확인하고, 통화 중에 주기 조회를 시작합니다. 통화 중 새 배포를 발견하면 안내만
표시하고 현재 세션을 유지합니다. 각 조회는 5초 후 취소합니다.

실제 입장 직전에 기존 시그널링 주소를 HTTP(S)로 바꾸고 `?compatibility=1`을 붙여
지원 기능을 조회합니다. 서버는 WebSocket 업그레이드가 없는 GET 요청만 처리해
`{"protocolVersion":3,"capabilities":["peer.reconnect","room.study","room.hand"]}`를 반환합니다.
응답에는 방·참가자 정보가 없으며 연결과 방 상태를 만들지 않습니다. BATON은 기존 쿠키
인증과 방 일치 검사를 먼저 통과해야 합니다. 별도 출처의 독립 실행 시그널링 서버를
사용할 때는 기존 허용 Origin에만 조회 응답을 허용합니다.
BATON 게이트웨이는 기존 시그널링 경로의 일반 GET 요청과 쿼리도 같은 서버로 전달해야 합니다.

웹은 프로토콜 버전과 필수 기능을 확인하고 추가 서버 기능은 허용합니다. 기존 v3 메시지
형태는 바꾸지 않았습니다. 이 조회를 지원하지 않는 서버에는 새 웹으로 입장할 수 없으므로
최초 도입 시 서버와 웹을 함께 배포해야 합니다. 새 버전 안내가 없는 이전 웹의 참가자도
한 번은 직접 새로고침해야 합니다. 미지원 기능을 끄고 입장하는 방식은 제공하지 않습니다.

## 통화 단축키와 채팅 검색

`Alt+Shift+M`은 마이크, `Alt+Shift+C`는 카메라, `Alt+Shift+H`는 손들기를 전환합니다.
Mac에서는 Alt 대신 Option을 사용합니다. 통화 중에만 동작하며 입력 칸, 편집 가능한 영역,
한글 조합, 설정 대화상자, 길게 누른 키와 사용할 수 없는 장치는 제외합니다. 장치 권한을
단축키로 요청하지 않습니다. 방을 나가면 키보드 이벤트를 해제합니다.

채팅 검색은 현재 브라우저에 남은 메시지 본문(기본 최대 200개)만 대상으로 하며 대소문자와
한글 유니코드 조합 차이를 정규화합니다. 원문과 링크는 유지하고 현재 선택한 메시지의 검색어를 강조합니다.
`Intl.Segmenter`로 표시할 문자 단위를 구분해 조합형 한글도 원문 위치에 표시하며,
URL 판별은 `linkifyjs`가 담당합니다. 링크 안의 검색어를 강조해도 주소와 복사 원문은 바뀌지 않습니다.
이전·다음 버튼 또는 Enter·Shift+Enter로 결과를 순환하고 Escape로 검색을 닫습니다.
한글 조합 중에는 검색 이동·닫기를 실행하지 않습니다. 검색 중 새 메시지가 와도
현재 결과와 스크롤을 유지하며, 검색을 닫으면 최신 대화로 이동합니다. 보관 한도를 넘긴
메시지는 검색 결과에서도 제거합니다. 검색어와 결과를 서버로 보내거나 저장하지 않습니다.
검색을 닫거나 메시지를 보내면 채팅 입력창으로 초점이 돌아옵니다.

## DataChannel 메시지와 수신 확인

`@round/protocol`은 브라우저 사이의 `chat.message`, `chat.ack`, `participant.media` 메시지 형식도
정의합니다. 채팅은 브라우저 간에 전달하며 메모리에만 보관합니다. Java 시그널링 서버는 이
메시지를 검사·중계·저장하거나 수신 확인에 응답하지 않습니다.

손들기 대기 순서는 시그널링 v3의 `room.hand.sync`, `room.hand.update`, `room.hand.state`로
관리합니다. 입장 뒤 `sync`로 구독하고, `update`에는 boolean `raised`만 보냅니다.
서버가 실제 요청자의 피어 ID를 사용하며 다른 참가자의 손을 대신 올리거나 내릴 수 없습니다.
서버는 기존 방 잠금 안에서 요청을 처리하고 전체 `peerIds` 순서와 `supportedPeerIds`,
단조 증가하는 `revision`을 구독자에게 보냅니다. 각 목록은 최대 6명이며 중복을 허용하지 않습니다.
참가자 이름은 현재 방 참가자 정보에서 찾고 기기의 시계로 순서를 정하지 않습니다.

같은 상태를 다시 요청해도 순서는 바뀌지 않습니다. 손을 내리거나 퇴장하면 제거하고 다시
손을 들면 맨 뒤에 추가합니다. 늦게 입장한 참가자는 현재 순서 전체를 받습니다.
서버 재연결 때 내 손들기 의사를 다시 보내되 이전 연결의 자리는 제거되므로 새 순서의
맨 뒤에서 대기합니다. 방 전체 재입장·새로고침은 손을 내린 상태로 시작합니다.
빈 방과 서버 종료 때 대기열을 삭제합니다. 웹은 이전 개정으로 최신 목록을 덮어쓰지 않습니다.

새 상태 메시지는 이 기능을 구독한 웹에만 전송합니다. 구버전용 `participant.hand`
DataChannel 전달도 유지하지만, 순서 지원 참가자의 상태는 서버 응답을 기준으로 표시합니다.
구버전 참가자가 보낸 손들기는 배지를 표시하고 해당 참가자에게 새로고침 후 재입장을 안내합니다.
공통 순서를 임의로 매기지 않습니다. 현재 웹은 입장 전에 서버의 `room.hand` 지원을 확인합니다.
모두 같은 대기 목록을 사용하려면 참가자 전원이 새로고침 후 다시 입장해야 합니다.

채팅 DataChannel은 `round-room` 라벨, `ordered=true`, 재전송 횟수와 수명 제한이 없는
신뢰성 전송 계약을 사용합니다. 원격 참가자가 이 계약과 다른 채널을 열면 브라우저는 해당
채널을 즉시 닫고 현재의 정상 채널을 유지합니다.

로컬 메시지는 대상인 모든 피어의 현재 `RoomSession`이 메시지를 검증·기록하고
`chat.ack`를 반환할 때까지 `pending`으로 남습니다. 이 확인 응답은 애플리케이션이
수락했다는 뜻이지, 사람이 메시지를 읽었다는 뜻은 아닙니다. 모든 대상의 확인 응답을 받으면
`sent`, 확인된 응답과 복구 불가능한 피어 실패가 함께 있으면 `partial`, 확인된 수신자가
없으면 `failed`가 됩니다. 재전송된 메시지는 `(peerId, messageId)`로 중복 표시를 막고
확인 응답은 다시 보냅니다. 연결 복구 중 확인 응답이 유실되어도 메시지를 한 번만 표시하면서
수신 상태를 갱신할 수 있습니다.

각 참가자는 확인되지 않은 채팅 프레임을 최대 50개까지 보유하며, 각 프레임에는 프로토콜의
32 KiB 상한과 전송 시도별 45초의 전달 기한이 적용됩니다. 브라우저는 DataChannel 송신 버퍼가
256 KiB를 넘기 전에 일반 채팅을 일시 중지하고, 64 KiB에서 `bufferedamountlow`가 발생한
뒤 재개합니다. 개수가 제한된 ACK 제어 프레임은 병합된 최신 미디어 상태와 대기 중인 채팅보다
먼저 전송합니다.

화면에 남은 로컬 채팅은 수신자별 상태도 보관합니다. 사용자는 최초 전송 후 2분 이내에
현재 같은 참가자 ID로 연결된 미확인 대상에게만 재전송할 수 있습니다. 이미 ACK한 대상과
늦은 입장·새 ID로 재입장한 대상은 제외합니다. 재전송은 같은 메시지 번호와 원문을 사용하며
시도별 45초 확인 기한을 다시 부여합니다. 재전송 가능 시간은 단조 증가 시계로 확인합니다.
`RoomChatLedger`는 연결 교체 이후에도 최근 16,384개의 `(peerId, messageId)`를 중복 제거합니다.
채팅 본문은 기존 기본 200개 보관 한도를 유지하며, 삭제된 메시지의 완료된 수신 상태도 제거합니다.

채팅 프레임의 `sentAt`은 화면 표시와 메시지 호환성에 사용하는 Unix 밀리초입니다. 참가자별
수신량 제한은 시스템 시각이 바뀌어도 영향받지 않는 단조 증가 시계를 사용합니다.

사용자가 연결 진단을 열거나 새로고침하면 `RoomSession`은 각 `RTCPeerConnection`의
표준 `getStats()`를 약 3초 간격으로 두 번 호출합니다. 같은 RTP 통계의 수신·손실 증가량으로
최근 수신 손실률을 계산하고 새 트랙·초기화된 카운터·누락된 통계는 계산에서 제외합니다.
표본이 없으면 0% 대신 측정 불가를 표시하며 연결 종료 시 측정 대기도 정리합니다. 화면에는
연결 상태, 로컬·원격 ICE 후보 유형, 마지막 왕복 지연, 최근 수신 손실률, 마지막 수신
지연 변동 최댓값과 재측정·네트워크 확인 안내를 표시합니다. 안내 기준은 손실 3% 이상 또는
지연 변동 30ms 이상, 왕복 지연 300ms 이상이며 원인을 확정하는 진단은 아닙니다.
진단 화면에는 현재 방의 참가자 이름을 붙여 문제가 있는 연결을 구분합니다. 이름은 현재 화면에서만
사용하고 복사하는 JSON에서는 제거합니다. 참가자 입장·퇴장 또는 연결 상태 변경 시 이전 결과와
진행 중인 측정을 폐기하고 재측정을 안내합니다. 측정 완료 시각은 화면에서 브라우저 시각으로
표시하고 화면과 클립보드의 지원용 JSON에는 같은 시각을 ISO 8601 형식으로 기록합니다. 방 코드,
참가자 ID, ICE 후보 주소와 포트는 결과에
포함하거나 서버로 전송하지 않습니다. 복사용 진단은 요청할 때만 측정합니다. 따라서 운영 지원에
필요한 TURN 사용 여부와 품질 정보는 복사할 수 있지만 참가자 이름과 네트워크 주소는 노출하지 않습니다.

발언·타일 품질 표시는 `ParticipantMonitor`에서 처리합니다. 활성 방의 보이는 탭에서
연결별 조회를 최대 약 0.5초마다 한 번 실행하고, 음성도 품질 표시도 필요 없으면 조회를 생략합니다.
원격 `inbound-rtp.audioLevel`과 제공되는 로컬 `media-source.audioLevel`이 0.02 이상으로
두 번 이어지면 발언 표시를 켜고 마지막 감지 후 0.8초 유지합니다. 음소거·연결 교체·퇴장·탭 숨김에
이전 결과를 지웁니다. 미지원 통계에는 발언 표시를 생략하며 녹음·서버 전송을 하지 않습니다.

사용자가 진단 패널에서 참가자별 수신 품질을 켜면 3초 간격의 RTP 증가량을 비교합니다.
손실 5% 이상, 왕복 지연 500ms 이상, 지연 변동 50ms 이상 중 하나가 두 구간 이어질 때
`수신 불안정`을 표시합니다. 정상 두 구간이면 해제하고 수신 표본이 없으면 `수신 품질 측정값 없음`으로 표시합니다.
이 임계값은 화면의 잦은 깜박임을 줄이기 위한 초기값이며 상세 진단 안내 기준과 별도입니다.
정적인 공유 화면의 프레임 증가량만으로 장애를 판단하지 않습니다. 참가자 대응은 현재 화면에서만
사용하고 복사용 진단에는 추가하지 않습니다. 자동 화질 변경은 하지 않습니다.

`chat.ack`는 피어 간 메시지이므로 Java 시그널링 프로토콜 버전을 변경하지 않습니다.
연결 시 수신 확인 기능의 지원 여부를 교환하지 않으므로, 웹 배포 후 참가자 전원이
새로고침해야 합니다. ACK를 구현하지 않은
구버전 ROUND도 채팅을 표시할 수 있지만, 발신자 화면에서는 45초 안에 수신 확인 응답이 없으면
**수신 미확인**으로 표시합니다.

채팅 본문은 `linkifyjs`로 HTTP·HTTPS 주소만 링크로 표시하며, HTML을 실행하거나
외부 미리보기를 요청하지 않습니다. 링크는 `noopener noreferrer`를 붙여 새 탭에서 엽니다.
메시지 복사는 Clipboard API로 줄바꿈을 포함한 원문을 복사하며, 권한이 없으면 직접 선택해
복사하도록 안내합니다. 전송 프레임과 휘발성 보관 정책은 바꾸지 않습니다.

채팅 화면은 사용자가 목록 하단을 보고 있을 때만 새 메시지를 따라갑니다. 이전 메시지를
읽는 동안에는 스크롤 위치를 유지하고 새 메시지·수신 미확인 메시지 개수와 최신 대화 이동 버튼을
표시합니다. 수신 ACK만 바뀌는 경우에는 스크롤하지 않습니다. 채팅을 다시 열거나 직접
메시지를 보내면 최신 대화로 이동합니다. 메시지 보관 한도와 휘발성 전달 방식은 그대로입니다.

채팅 입력창은 내용과 화면 너비에 맞춰 최대 112px(약 5줄)까지 늘어나고, 전송 후에는
한 줄 높이로 돌아갑니다. Enter는 전송, Shift+Enter는 줄바꿈이며 한글 조합 중 Enter는
전송하지 않습니다. 기존 웹 입력 한도 1,000자를 유지하고 현재 길이와 한도 도달을 표시합니다.
길이는 기존 `maxLength`와 같은 UTF-16 코드 단위로 계산하므로 일부 이모지는 2자 이상입니다.
붙여넣기는 선택한 영역을 교체한 뒤의 길이와 줄바꿈 정규화를 반영합니다. 한도를 넘으면
붙여넣기 전체를 취소하고 안내하며, 기존 입력과 선택을 유지합니다. 프로토콜의 4,000자
수신·전송 검증 한도와 휘발성 보관 정책은 변경하지 않습니다.

작성 중인 채팅이 있거나 화면 공유 중일 때 방의 **나가기** 버튼을 누르면 종료 확인 창을
표시합니다. 계속 참여하기와 Esc는 입력·연결을 유지하며 확인한 뒤에만 나갑니다.
오류 화면의 **다시 연결**과 참가자 연결 실패 안내의 **방 다시 입장**에도 같은 조건으로
재입장 확인창을 표시합니다. 현재 연결을 종료하고 입장 준비로 돌아가며 초안·대화 기록·
공유가 유지되지 않음을 안내합니다. 취소와 Esc는 현재 방을 유지하고, 승인은 재입장을
한 번만 실행합니다. 참가자별 다시 연결과 자동 복구에는 이 확인을 추가하지 않습니다.
ROUND가 만든 같은 문서의 이동 기록에서 뒤로가기·앞으로가기로 방을 벗어날 때도 같은
확인창을 사용합니다. 이동 기록에 문서 식별자와 순번을 보관하고, 확인 중에는 방 컴포넌트를
해제하지 않은 채 원래 이동 위치로 돌아옵니다. 취소는 주소·초안·통화를 유지하고, 승인은
사용자가 요청한 이동을 한 번 적용합니다. 확인 중 반복한 이동은 원래 위치로 복구합니다.
다른 문서로 나가는 직접 초대의 뒤로가기는 아래 브라우저 종료 경고가 처리합니다.
같은 조건일 때만 `beforeunload`를 등록해 새로고침·탭 닫기에 브라우저 경고를 요청합니다.
확인 창에서 이미 퇴장을 승인한 경우에는 다시 경고하지 않습니다. 강제 인증 종료와
자동 연결 복구에는 확인 창을 띄우지 않습니다. 메시지를 자동 저장하는 기능은 아닙니다.
브라우저 자체 경고는 모바일 앱 강제 종료 등에서 보장되지 않고 문구도 브라우저가 정합니다.
[MDN의 beforeunload 제한](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeunload_event)을 따릅니다.

## 선택형 화면 켜짐 유지

통화 장치 설정의 **통화 중 화면 켜짐 유지**는 기본으로 꺼져 있고, 사용자가 켠 현재 방에서만
유지합니다. 설정창을 닫아도 유지하며 퇴장·연결 중단 때 해제합니다. 연결이 복구되거나
탭으로 돌아오면 설정이 켜져 있고 화면이 보일 때만 다시 요청합니다. 설정을 끄거나 방을
나간 뒤 늦게 승인된 요청도 즉시 해제합니다.

설정 여부와 실제 적용 상태를 구분해 요청 중·적용 중·대기·해제·실패를 표시합니다.
미지원 브라우저에서는 조작을 비활성화하고, 시스템이 해제하거나 요청을 거절했을 때
적용 중으로 표시하지 않습니다. 브라우저의 화면 유지 기능만 사용하며 백그라운드 통화,
사용자의 수동 잠금 방지나 배터리 절약 설정 무시를 보장하지 않습니다.
[MDN의 Screen Wake Lock 설명](https://developer.mozilla.org/en-US/docs/Web/API/Screen_Wake_Lock_API)을 따릅니다.

## 미디어 입력과 자원 관리

입장 전 화면과 통화 장치 설정은 같은 마이크 입력 표시를 사용합니다. 이미 허용받은 현재
트랙을 Web Audio `AnalyserNode`로 분석하며, 출력 장치에 연결하거나 녹음·추가 전송·추가 권한
요청을 하지 않습니다. 통화 중에는 장치 설정을 열었을 때만 분석하며, 목록에서 선택만 한 장치가
아닌 실제 적용된 마이크의 입력을 표시합니다. 트랙 교체·음소거·화면 종료 시 분석 노드와
`AudioContext`만 정리하고 트랙 관리 주체와 기존 통화 송신은 변경하지 않습니다.

입장 전 장치 선택은 실제 사용 중인 트랙이 같은 장치일 때만 요청을 생략합니다. 사용 가능한
트랙이 없으면 목록의 기본 선택과 관계없이 선택 안내를 표시해 장치를 다시 요청할 수 있게 합니다.

입장 전 장치가 분리돼도 마이크·카메라의 마지막 켜기·끄기 선택을 방 세션에 전달합니다.
따라서 입장 후 장치를 다시 선택해도 꺼 둔 입력이 자동으로 켜지지 않습니다. 장치 확인 없이
카메라·마이크 없이 입장한 경우에는 기존처럼 처음 선택한 장치를 켭니다.

통화 중 입력 장치는 `RoomSession.selectInputDevice`가 새 트랙을 얻고 기존 송신자의
`replaceTrack`으로 교체합니다. 기존 트랙은 모든 교체가 끝난 뒤 해제하며 음소거 상태를
유지합니다. 실패하면 기존 트랙으로 복원하고, 복원까지 실패한 피어 연결만 다시 만듭니다.
장치가 분리돼도 마지막 켜기·끄기 선택을 유지하며, 장치가 없는 동안 받은 방장 끄기 요청도
다음 장치에 적용합니다. 사용자가 다시 켜면 이후 장치 교체에는 변경된 선택을 적용합니다.
단절 기록은 마이크와 카메라별로 보관하며 해당 장치를 복구해야 해제합니다. 다른 연결 경고가
먼저 표시되더라도 장치 단절 기록은 유지하고, 그 경고가 해결되면 남은 장치 복구 안내를 표시합니다.
교체나 복원 중 피어가 종료되면 해당 대기를 취소하고 남은 피어만 처리합니다.
처음 장치를 켜는 경우에는 `addTrack`과 추가 협상을 사용합니다. 기존 방 세션과 채팅 기록은
유지하며 화면 공유 중에는 마이크만 바꿀 수 있습니다. BATON 참여권은 새 장치 요청 전에 확인합니다.

통화 장치 설정의 카메라 송신 모드는 `RTCRtpSender.setParameters()`로 적용합니다. 일반은
브라우저의 송신 제어를 사용하고 데이터 절약은 연결별 카메라 영상을 최대 150kbps·10fps,
가로·세로 절반 크기로 제한합니다. 기본 입력 기준으로 약 320×180이며 실제 송신량은
네트워크·브라우저에 따라 더 낮을 수 있습니다. 오디오·수신 영상·로컬 미리보기는 바꾸지
않습니다. 화면 공유에는 이 제한을 해제하고 카메라 복귀 시 다시 적용합니다. 선택은 새 피어와
재연결에도 유지하지만 방을 나가면 초기화합니다. 일부 연결이 설정을 거부하면 통화는 유지하고
재적용 또는 카메라 끄기를 안내합니다. 자동 네트워크 판정과 SDP 직접 수정은 하지 않습니다.

스피커 선택은 브라우저 화면에서만 관리하며 `RoomSession`과 송신 트랙은 변경하지 않습니다.
`HTMLMediaElement.setSinkId`로 기존·신규 원격 영상에 적용하고, 지원되는 환경에서는 사용자
버튼으로 `selectAudioOutput` 선택창도 열 수 있습니다. 출력 선택만을 위해 마이크 권한을 요청하지 않습니다.
적용 전에는 원격 음성을 음소거하고, 실패하면 다른 출력으로 우회하지 않고 설정 안내를 표시합니다.
동일 장치를 다시 적용해도 재시도합니다. 선택한 장치가 분리되면 알림을 표시하며 시스템 스피커로
자동 전환하지 않습니다. 미지원 브라우저는 시스템 기본 출력을 사용하고 운영체제 설정을 안내합니다.
선택은 방 화면을 벗어나면 버리며 장치 ID를 저장하거나 서버에 보내지 않습니다.

참가자 타일의 **음량** 메뉴에서 0~100% 범위로 내가 듣는 음량을 조절합니다.
`HTMLMediaElement.volume`만 바꾸므로 재생이나 연결을 다시 시작하지 않습니다.
음량 변경을 무시하거나 거부하는 브라우저에서는 막대를 비활성화하고 기기 음량을 안내합니다.
브라우저 지원 범위는 [MDN의 volume 설명](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/volume)을 참고합니다.
메뉴의 **소리 끄기**는 해당 영상 요소의 `muted`만 바꿉니다. 상대의 마이크와 다른
참가자의 재생에는 영향을 주지 않으며 방장의 마이크 끄기 요청과 별개입니다. 같은 참가자의
스트림·스피커 교체와 카메라 끄기 뒤에도 유지하지만, 참가자 퇴장이나 새 연결로 타일이
교체되면 초기화합니다. 음소거를 풀면 이전에 정한 음량으로 듣습니다. 음량과 개인 음소거
상태를 저장하거나 서버로 보내지 않습니다.

내 참가자 타일의 **내 영상 숨기기**는 내 미리보기만 가립니다. 영상 요소, 트랙과 송신은
유지하며 카메라 끄기와 구분해서 안내합니다. 숨긴 상태는 장치 교체와 카메라·화면 공유 전환에도
유지하고 **내 영상 다시 보기**로 복구합니다. 방 화면을 벗어나면 초기화합니다.

입장 준비와 통화 중 내 카메라 미리보기는 같은 방향으로 보이도록 좌우 반전합니다. 상대에게
보내는 영상은 바꾸지 않으며 상대 영상과 내·상대 화면 공유도 원본 방향으로 표시합니다.

확인음은 사용자가 누른 뒤에만 Web Audio의 `OscillatorNode`로 0.6초 재생합니다.
`MediaStreamAudioDestinationNode`와 오디오 요소를 사용해 통화와 같은 출력 장치로 보내며,
완료·실패·설정 닫기 시 확인음 스트림과 `AudioContext`를 정리합니다.

`RoomSession`은 한 번에 하나의 영상 입력을 전송합니다. 화면 공유를 시작하면 공유 트랙으로
모든 기존 `RTCRtpSender`의 카메라 트랙을 교체합니다. 화면 공유를 중지하거나 브라우저의
**공유 중지**를 누르면 보관해 둔 카메라 트랙으로 돌아갑니다. 마이크 트랙은 그대로 유지합니다.
공유 중에는 카메라 전환을 막아 보이지 않는 카메라 설정이 바뀌지 않게 합니다. 새 참가자에게도
현재 선택된 영상을 전송하며, `participant.media` 메시지로 영상 입력이 `camera`인지
`screen`인지 알립니다.

공유 시작 전에 통화 장치 설정에서 일반(최대 1280×720, 15fps, `detail`) 또는
문서·코드(최대 1920×1080, 10fps, `text`)를 선택합니다. 설정은 브라우저 캡처 제약과
콘텐츠 힌트이며 실제 해상도·가독성을 보장하지 않습니다. 공유 중에는 선택을 막고,
중지 후 다음 공유부터 새 설정을 사용합니다. 카메라용 데이터 절약 모드는 화면 공유에 적용하지 않습니다.

수신한 공유 화면은 한 개를 크게 고정할 수 있습니다. 고정은 해당 브라우저의 배치만 바꾸며
영상 요소와 `MediaStream`을 유지합니다. 채팅을 열거나 전체 화면으로 전환할 수 있고,
공유가 끝나거나 해당 참가자가 나가면 고정을 해제합니다. 고정 선택은 서버로 보내거나 저장하지 않습니다.
수신 화면은 50% 단위로 1~4배 확대하고 끌기 또는 방향키로 이동할 수 있습니다.
배율 버튼이나 키보드 `0`으로 위치와 배율을 초기화하며 `+`·`-`로 배율을 바꿉니다.
확대 중에는 화면 위의 터치 이동을 화면 끌기에 사용합니다. 페이지 스크롤은 타일 바깥에서 하거나
100%로 돌아간 뒤 사용할 수 있습니다. 공유 종료와 수신 스트림 교체 때 확대 상태를 초기화합니다.
표준 전체 화면을 지원하면 확대 도구도 함께 표시합니다. 브라우저가 영상 자체 전체 화면만
허용하면 원래 화면 비율로 표시하고, 전체 화면을 닫으면 기존 확대 설정으로 돌아옵니다.
도구를 함께 표시하는 전체 화면에는 **전체 화면 닫기** 버튼을 제공합니다. 브라우저의
`fullscreenchange`와 Safari 종료 이벤트를 구독해 Esc·브라우저 조작으로 닫아도 버튼을
원래 상태로 돌립니다. 브라우저 자체 영상 전체 화면에서는 브라우저의 닫기 기능을 사용합니다.
화면 확대는 받은 영상의 표시 크기만 바꾸므로 송신 화질과 해상도를 높이지 않습니다.

방장은 다른 참가자의 마이크·영상을 끄도록 요청할 수 있습니다. 시그널링 프로토콜 v3는 입장이
승인된 참가자에게 `host|participant` 역할을 부여합니다. 서버는 끄기 명령을 보내기 전에 요청자,
대상, 방과 역할을 검증합니다. 장치를 다시 켜는 것은 해당 참가자만 할 수 있으며, 다른 참가자는
마이크·카메라·화면 공유를 켤 수 없습니다. 독립 실행 모드는 선택 입력한 방장 키를
`ROUND_STANDALONE_HOST_TOKEN_SHA256`과 대조하고 판정한 역할만 보관합니다.
BATON 모드는 검증된 참여권의 `role`을 기준으로 권한을 판단하며 독립 실행 방장 키는 거부합니다.

이 기능은 서로 신뢰하는 소규모 스터디를 위한 것입니다. 영상·음성은 참가자 간에 전송되므로
변조된 브라우저는 끄기 명령을 무시할 수 있습니다. 강제 퇴장이나 서버에서 지속적으로 송신을
차단하는 기능에는 퇴장·재입장 차단 정책 또는 미디어를 중계하는 SFU가 필요합니다.

## 사용자 식별과 입장 권한

BATON은 사용자, 스터디, 일정과 입장 권한을 관리합니다. ROUND는 메모리에 보관하는 방·참가자 상태,
WebSocket 시그널링과 TURN 자격 증명 발급을 담당하며 BATON의 데이터베이스나 엔티티를
참조하지 않습니다. 승인 결과는 해당 방에서만 쓸 수 있는 단기 RS256 참여권으로 전달하고 ROUND가 공개
JWK로 로컬 검증합니다.

| 목적               | 동일 출처 공개 경로                                 | 처리 서비스·내부 경로                  |
| ------------------ | --------------------------------------------------- | -------------------------------------- |
| 참여권 갱신        | `/round/rooms/{roomId}/participation-grant/refresh` | BATON이 직접 처리                      |
| WebSocket 시그널링 | `/round/rooms/{roomId}/signal`                      | `/rooms/{roomId}/signal`               |
| TURN 자격 증명     | `/round/rooms/{roomId}/turn-credentials`            | `/api/rooms/{roomId}/turn-credentials` |

참여권은 URL, JavaScript 또는 브라우저 저장소에 노출하지 않고 방별 호스트 전용 쿠키로
전달합니다. 공개 경로, 내부 경로, `room.join`과 참여권의 방 식별자가 모두 일치해야 하며,
사용자 식별자는 로그인 공급자 값이 아닌 BATON 내부 `Account.id`를 사용합니다. 키
교체, 클레임, 수명, 시계 처리, 오류 상태와 갱신 응답의 상세 계약은
[ADR 0001](adr/0001-round-independent-service.md)을 단일 원본으로 사용합니다.

WebSocket의 만료 시점은 연결 당시 검증한 참여권으로 고정됩니다. 만료된 연결은 기존 종료
절차로 한 번만 정리합니다. 새 참여권으로 재연결할 때만 기존 연결과 잠시 겹치도록 허용합니다.
같은 사용자의 새 연결이 방에 입장하면 더 최근 연결을 남기고 이전 연결을 닫습니다.
이전 연결은 자동 재연결하지 않습니다. 독립 실행 모드에는 참여권 만료와 사용자별 연결 제한을 적용하지 않습니다.

BATON 웹은 로그인 세션과 현재 방 참여권을 확인하기 전 입장 준비 화면과 장치 권한
요청을 열지 않습니다. 갱신 관리자는 중복 요청을 하나로 합치고, TURN 갱신과 WebSocket
연결·재연결 전에 최신 참여권을 확인합니다. 인증·권한·방 종료 응답은 각각 로그인 안내,
BATON 복귀, 종료 화면으로 전환하며 내부 응답이나 자격 증명을 사용자 화면에 노출하지
않습니다.

## 운영 배포 조건

`localhost`에서는 TLS 없이 카메라, 마이크, 화면 공유를 사용할 수 있습니다. 배포된
환경에서는 HTTPS/WSS를 사용하고 `Permissions-Policy`에서 `camera`, `microphone`과 함께
`display-capture`를 허용해야 합니다. 제한적인 NAT 또는 회사 네트워크 뒤의 사용자를 위해
프로덕션 배포에는 TURN 서비스도 필요합니다. STUN만으로 연결을 보장할 수 없습니다.

Caddy는 유일한 공개 HTTP 진입점입니다. 독립 실행 모드에서는 웹 화면,
`/signal`, `/api/turn-credentials`에 공유 접근 인증을 요구합니다. 요청을 프록시하기 전에
Authorization 헤더를 제거하며, 상태 확인용으로는 `/healthz`만 공개합니다. BATON 모드에서는
공통 외부 프록시가 같은 출처의 방별 공개 경로를 ROUND에 연결하고, Spring Security가 시그널링과
TURN 처리 전에 참여권 쿠키를 검증합니다. 참여권 갱신은 BATON이 직접 처리하며 사용자 신원과
현재 스터디 참여 권한을 다시 확인합니다.
BATON용 웹 빌드는 `VITE_ROUND_AUTH_MODE=baton`을 사용합니다. 브라우저는 같은 방 ID로
세 경로를 구성하고 개별 경로를 덮어쓰는 설정을 거부합니다. BATON 모드에서는 독립 실행용
연결 설정을 사용할 수 없습니다.

방 상태, 연결 슬롯 예약과 TURN 발급 횟수는 각 서버의 메모리에 저장합니다. 여러 시그널링
서버를 실행하려면 이 상태의 공유 저장소, 방별 요청 라우팅과 서버 간 메시지 중계가 필요합니다.
이 준비 없이 서버를 늘리면 같은 방이 여러 서버로 나뉘고 참가자 제한도 각각 적용됩니다.
참여권은 WebSocket 연결과 방 입장 때 검사하며, 연결은 참여권의 `exp`까지만 유효합니다.
BATON에서 참여 권한을 취소하면 다음 갱신에서 반영됩니다. 이미 연결된 WebSocket은 현재의
단기 참여권이 만료될 때까지 승인 상태를 유지할 수 있습니다.

Cloudflare TURN API 토큰은 시그널링 서버에서만 사용합니다. 브라우저는 독립 실행
모드에서는 `/api/turn-credentials`, BATON 모드에서는 방별 API에서 단기 자격 증명을
요청합니다. API 토큰이나 장기 자격 증명은 Vite 번들에 넣지 않습니다. 시그널링 서버는
인증·Origin 검사와 발급 한도 검사를 통과한 요청만 Cloudflare 자격 증명 API로 전달합니다.
공급자 장애 시 503을 반환하고 오류 횟수를 집계합니다.
BATON 모드는 고정 집계 구간의 유효 클라이언트 IP·`(room_id, sub)`·서버 전체 한도를 모두
통과할 때만 함께 차감합니다. 새 `jti` 발급이나 IP 변경으로 참가자 발급 횟수가 초기화되지 않습니다.
독립 실행 모드에는 IP와 서버 전체 한도만 적용합니다. 발급 제한 지표에는 참가자·방·토큰·IP를
남기지 않고 정해진 `scope` 값만 사용합니다.

서비스별 역할과 전체 클레임 계약은
[ADR 0001](adr/0001-round-independent-service.md)에 기록되어 있습니다.

## 연결 복구와 자원 정리

입장 전에는 준비 화면이 카메라·마이크 트랙을 관리합니다. 입장하면 `RoomSession`이 관리를
맡습니다. `RoomSession`은 정해진 횟수만큼 시그널링 재연결을 시도하는 동안 내 미디어 트랙을
유지하고, 이전 원격 참가자 연결과 서버가 발급했던 피어 ID를 버립니다. 퇴장하거나
재연결 시도를 모두 소진하면 관리 중인 모든 트랙과 타이머를 중지합니다.

BATON 모드는 로그인 세션과 참여권을 확인한 뒤 입장 준비 화면을 표시합니다. 사용자가
미디어 사용 여부를 정하고 입장을 실행하면 TURN 자격 증명을 발급하고 WebSocket을 만듭니다.
로그인이 필요하면 로그인 후 동일 출처의 정규 `/room/{roomId}`로 복귀합니다. 참여 권한이
없으면 로그인을 반복시키지 않고 BATON으로 안내합니다.

입장 권한을 확인할 때 만든 갱신 관리자를 통화 중에도 재사용해, 입장 직후 참여권을 다시
발급하지 않습니다. 동시에 발생한 갱신 요청은 하나로 합칩니다. 다음 갱신은 BATON이 반환한
대기 시간 `refreshAfterSeconds`와 브라우저의 단조 증가 시계로 예약합니다. 준비 화면에서
갱신 시점이 지나면 장치 접근과 두 입장 방식 모두 실행 전에 참여권을 다시 확인합니다.
통화 중 갱신 응답이 `401`, `403`, `404`이면 갱신을 중단하고 각각 로그인, 권한 없음,
방을 찾을 수 없다는 안내를 표시합니다. 지원하지 않는 인증 모드 설정은 첫 화면을 표시하기
전에 오류로 처리합니다. BATON 모드의 통화용 이름은 페이지 메모리에만 보관합니다.

TURN API도 서버가 계산한 `refreshAfterSeconds`를 반환합니다. 브라우저는 응답 수신 시점의
단조 증가 시계에 이 값을 더해 갱신 시점을 정하며, `expiresAt`과 `Date.now()`의 차이로
계산하지 않습니다. TURN 갱신과 WebSocket 최초 연결·재연결은 모두 먼저 참여권의
`ensureFresh()`를 호출합니다. 참여권 갱신에 성공하면 `HttpOnly` 쿠키만 교체하고 현재
WebSocket은 유지합니다. 기존 참여권이 만료되면 ROUND가 연결을 닫고, 브라우저는 정해진
재연결 절차에 따라 내 미디어와 채팅 기록을 유지한 채 새 쿠키로 다시 연결합니다.

BATON 웹 서버는 파일명에 해시가 붙은 `/round-ui/assets/*`에만 1년 불변(`immutable`) 캐시 정책을
적용합니다. 방 HTML은 `no-store`로 제공합니다. `/round-ui/`는 본문을 캐시하지 않는 404를
반환하며, 개발·검증용 방 생성·초대 코드 입력 화면을 표시하지 않습니다.

ICE 복구 시 양쪽이 동시에 offer를 보내 충돌하지 않도록 참가자 쌍마다 offer를 보낼 쪽을
정합니다. 연결이 끊기면 잠시 기다린 뒤 ICE restart를 수행하고, 복구되지 않으면 피어 연결을
다시 만듭니다. ROUND는 offer마다 형식이 제한된 `negotiationId`를 붙이고, answer와 ICE 후보는
같은 값을 돌려줍니다. 다시 만든 연결은 이전 `negotiationId`의 메시지를 거부해 늦게 도착한
SDP·ICE가 새 연결을 방해하지 않도록 합니다.
`negotiationId`는 프로토콜 v2에서 도입됐고 현재 계약은 관리 메시지를 포함한 v3입니다.
이 필드는 선택 항목이지만 현재 ROUND 클라이언트는 항상 보냅니다. 웹과 시그널링 서버는 함께
배포해야 합니다. 참가자 한도를 늘리거나 여러 영상 소스를 추가할 때는 메시 구조를 계속 확장하지
말고 SFU 방식으로 전환해야 합니다.
