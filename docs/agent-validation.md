# 에이전트 검증 절차

## 2단계 피드백 루프

작업을 시작할 때 기준 커밋을 기록한다. 변경 종류별로 커밋한 뒤에도 이 기준부터 전체 작업을
다시 볼 수 있어야 한다.

### 작성 직후

파일이나 함께 컴파일되는 최소 묶음을 작성하면 다음 순서로 확인한다.

1. `git diff -- <경로>`로 의도하지 않은 수정과 주변 규칙 위반을 확인한다.
2. 문서·설정·TypeScript는 `npx prettier --check --ignore-unknown <경로>`로 형식을 확인한다.
3. TypeScript는 변경 패키지의 타입 검사와 가장 가까운 테스트를 실행한다.
4. Java 운영 코드는 `compileJava`, 테스트 코드는 `compileTestJava`를 실행하고 변경 동작의 관련 테스트를 선택한다.

### 작업 종료 직전

1. `git status --short`로 누락한 새 파일과 예상하지 않은 변경을 확인한다. `git diff`에
   나타나지 않는 미추적 파일은 내용을 따로 읽거나 스테이징한 뒤 전체 차이에 포함한다.
2. `git diff --check <기준 커밋> --`로 전체 공백 오류를 확인한다.
3. `git diff <기준 커밋> --`를 읽고 계층 의존, 책임 배치, 공개 계약, 문서와 테스트의 누락을 확인한다.
4. Java 소스나 빌드 설정을 바꿨으면 `npm run check:architecture`로 패키지 경계를 확인한다. 같은 리비전에서 `npm run check:java`가 통과했다면 다시 실행하지 않는다.

ArchUnit 검사는 구조 규칙만 확인한다. 변경 동작의 테스트와 Spring 컨텍스트 검사를 대신하지 않는다.

## 검사 선택

변경 파일과 확인할 동작을 먼저 정한다. 테스트 파일은 `rg --files`로 현재 저장소에서 찾는다.

- 문서·문구만 바뀌면 변경 파일의 형식·차이와 관련 기존 문구 검사를 확인한다.
- 작은 웹 수정: `npm run check:web -- src/components/VideoTile.test.tsx`. 파일은 여러 개 지정할 수 있으며 `apps/web` 기준이다. 인자를 생략하면 웹 전체 테스트를 실행한다.
- 웹 전체 확인: `npm run check:web`. 배포 번들이 바뀌면 웹 빌드를 실행한다. 웹 빌드에 타입 검사가 포함되므로 바로 앞뒤로 같은 타입 검사를 반복하지 않는다.
- Java 수정: `./gradlew --no-daemon :apps:signaling:test --tests '<대상 클래스>'`. 서버 전체 테스트와 배포 파일이 필요하면 `npm run check:java`로 한 번에 실행한다.
- Java 계층 확인: `npm run check:architecture`. `ArchitectureTest`는 일반 서버 테스트에도 포함된다.
- 여러 TypeScript 패키지 확인: `npm run check:typescript`. 프로토콜·RTC 코어의 타입 검사에는 테스트 코드도 포함되므로 유지한다.
- 전체 확인: `npm run check`. 브라우저 검사는 입장·통화 등 바뀐 동작에 해당하는 `e2e/` 파일과 프로젝트만 선택한다.

Vitest 파일 지정은 영향받는 테스트를 자동으로 모두 찾아주는 기능이 아니다. 공용 코드나 설정이 바뀌면 해당 패키지 또는 전체 검사로 범위를 넓힌다.
테스트가 없다는 결과를 통과로 처리하는 옵션은 사용하지 않는다.

## 실패 처리

- 테스트의 기대값 불일치·타입 오류: 코드를 확인하고 수정 후 실패한 검사부터 실행한다.
- `EPERM`, `EACCES`, Gradle 캐시 잠금 파일 접근 실패: 실행 환경 문제다. 이 Mac의 제한된 실행 환경에서 로컬 서버·브라우저·Gradle 캐시 접근이 필요한 검사는 도구의 권한 승인을 받아 실행한다. 거부되면 원인과 미검증 범위를 남긴다.
- 서버 시작 실패처럼 원인이 안 보이면 해당 로그만 한 번 확인한다. 원인이 확인된 뒤에는 같은 환경에서 전체 검사를 다시 시작하지 않는다.
- 포트 점유: 실행 중인 작업과 서버 설정을 먼저 확인한다. 다른 작업의 서버를 종료하거나 인증 모드가 다른 서버를 재사용하지 않는다.
- 경로·옵션·도구 응답 오류: 파일 목록이나 해당 명령의 도움말을 확인한다. 검색 결과가 없는 상태와 명령 실패를 구분하고, 도구 오류 텍스트를 JSON으로 가정하지 않는다.
- Python `yaml` 모듈이 없으면 같은 환경의 다른 Python으로 반복하지 않는다. 이 저장소에 설치된 Node `yaml`을 사용하는 등 필요한 확인만 수행한다.

## 다음 작업에 남길 기록

실행한 검사의 결과를 `output/agent-validation.md`에 갱신한다. 이 파일은 Git에서 제외되며, 원본 세션이나 비밀값은 복사하지 않는다.

- 기준 커밋과 검사 당시 변경 파일
- 실행 명령, 확인 범위, 통과·실패·미실행 결과
- 환경 실패의 원인과 해결한 조건
- 아직 확인하지 않은 동작과 다시 검사해야 할 변경 조건

다음 작업은 기록과 현재 차이를 비교한다. 관련 소스·설정·의존성·실행 환경이 바뀌었거나 기록이 불명확하면 해당 검사를 다시 실행한다.
문서 수정이나 커밋만으로 이미 통과한 코드 검사를 무효로 보지 않는다. 이 기록으로 CI나 실제 외부망 검증을 대체하지 않는다.

## 기존 세션에서 확인한 낭비

검토일: 2026-09-05. 아래 세션의 관련 작업 기록을 확인했다.

- **기능 개선 사항 검토**: 최근 문구 수정 두 차례에서 각각 웹 테스트 226개와 브라우저 검사 9개를 실행했다. 작은 수정에는 대상 테스트를 선택하도록 바꿨다. 같은 실행 권한 문제로 브라우저 검사가 두 번 실패한 기록도 확인해 환경 실패 재시도 기준을 추가했다.
- **WebRTC MVP 프로젝트 시작**: 화면 공유·방장 제어는 브라우저와 서버를 함께 바꾼 작업이었다. 이런 변경의 전체 계약·브라우저 검증은 유지한다.
- **WebRTC MVP 프로젝트 시작 (2)**: 서버 리팩터링과 Vite 프록시 수정의 검증 요약을 확인했다. 오래된 기록에는 개별 실행 출력이 충분하지 않아 같은 검사 재실행 횟수를 단정하지 않았다.

현재 검사 명령에서도 중복을 확인했다. `npm run check`의 프로토콜 빌드는 2회에서 1회,
웹 타입 검사는 2회에서 1회, Gradle 호출은 3회에서 1회로 합쳤다. 기존 검사 범위는 유지한다.
조회 자체의 낭비를 줄이기 위해 이미 읽은 문서 재사용, 현재 경로 확인, 세션 출력 요약도 저장소 지시에 포함했다.
